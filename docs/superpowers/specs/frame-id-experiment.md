# Эксперимент: идентификатор кадра (Task 1)

Дата: 2026-10-28. Итог: **метка в пикселях принята** (вариант (a) спецификации). Запасной
вариант WebCodecs + DataChannel не нужен.

## Конструкция метки

Код: `backend/app/contracts/frame_id.py`; векторы для порта на TypeScript:
`tests/fixtures/frame_id_vectors.json` (формат и порядок бит — `tests/fixtures/README.md`).

- Кодовое слово 40 бит: `frame_id` (32 бита, старший бит первым) + CRC8 (старший первым).
  CRC-8/I-432-1: poly 0x07, init 0x00, xorout 0x55, по 4 байтам id big-endian
  (xorout ≠ 0 — сплошная чёрная или белая полоса сверху, типичная для эндоскопа, не читается как id).
- Бит = сплошной блок 16×16 в строках 0..15: 1 — белый (255), 0 — чёрный (0). Блоки
  выровнены по сетке макроблоков H.264 и по 8×8 хромы 4:2:0; сигнал только в яркости.
- Избыточность: слово повторяется `min(3, ширина // 640)` раз слева направо
  (при 1920 px три копии занимают ровно всю верхнюю полосу 1920×16).
- Чтение: средняя яркость внутренних 8×8 каждого блока; по каждому биту среднее
  (яркость − 128) по копиям (мягкое голосование); бит = знак. Если у какого-то бита
  |отклонение| < 40 или CRC не сходится — `None`.
- `strip_marker`: строки 0..15 заменяются копией строки 16 (форма кадра не меняется).

## Методика

PyAV 17.1 / libx264, 1920×1080, 30 к/с, yuv420p, `preset=veryfast tune=zerolatency`,
`maxrate=битрейт`, `bufsize=битрейт/2`, GOP 300. 1000 кадров на прогон, содержимое —
прокручивающийся градиент + движущаяся шумовая текстура (0..47) + движущийся диск с XOR
(тяжелее реального эндоскопического видео). id — псевдослучайные uint32, т.е. меняются все биты.
Скрипт тестов: `tests/test_frame_id.py::test_survives_h264` (≈18 с на битрейт, весь файл ≈80 с).

## Найденный режим отказа: «устаревшая» метка

Все неверные чтения ниже 500 кбит/с (250 и 150 кбит/с) — **не мусор, а id одного из
предыдущих кадров** (CRC верный): при нехватке бит кодер пропускает макроблоки верхней
полосы (P_Skip) и декодер показывает метку прошлого кадра; чаще всего сразу после
ключевого кадра, который съедает буфер. Ложных id, которых не было в потоке, не встречено.

Требование к серверу (Task 7): принимать id только если он строго больше последнего
принятого (клиент нумерует кадры монотонно); иначе считать кадр без id. Это убирает
весь наблюдаемый класс ошибок. Также для отправителя: `degradationPreference =
"maintain-resolution"`, иначе WebRTC при падении полосы уменьшит разрешение и геометрия
блоков сломается (чтение даст `None`, не ложный id — но кадры будут без id).

## Ограничения

- Проверен libx264 как модель кодека; реальные кодеры браузера (OpenH264, аппаратные,
  VP8/VP9 при иных договорённостях SDP) не проверялись — повторить на живом WebRTC в Task 7/9.
- Порог 40 при трёх копиях: исправление одной полностью инвертированной копии проходит
  с запасом всего ~2 (|±42.5| против 40).
