# Клиент AIIRISDX: дизайн

Дата: 2026-10-28. Статус: черновик на утверждение.

Пометки: **[решено]** — решение заказчика; **[моё]** — допущение автора, требует проверки.

## 1. Цель и зачем

Серверный клиент, который принимает эндоскопическое видео в реальном времени (WebRTC из браузера на компьютере у стойки) или из предзаписанного файла, прогоняет его через каскад ML-моделей и выдаёт:

1. Вторичный экран для врача: кадр с небольшой задержкой вместе с точно совпадающими bbox, сигнализация о находках. Врач ориентируется по штатному монитору стойки, наш экран вторичный. **[решено]**
2. Результат сессии: чистое видео (без запечённых рамок) и синхронизированный лог bbox и свойств. Лог пригоден для повторной обработки и дообучения моделей. **[решено]**

Источники и референсы:
- `/mnt/work-disk/Documents/Dev/video_stream_client/video_stream_project` — прототип, только как костяк. Его главные хронические проблемы: рассинхронизация кадра и bbox (нет общего идентификатора кадра, сопоставление по эвристике времени с допуском 0,5 с, показ «последнего пришедшего» набора); инференс внутри event loop соединения; нет масштабирования.
- `/mnt/work-disk/Documents/Dev/endoscopy-platform` (Clinotate, FastAPI/React/Celery, Apache-2.0) — сборка датасетов, обучение, оценка. Сейчас обучает только Ultralytics YOLO11 (classification, detection, segmentation); экспортирует только `best.pt`; рантайма для клиента нет.

## 2. Цели, не-цели, анти-цели

Цели:
- Точное совпадение кадра и его bbox на экране за счёт жёсткой привязки по идентификатору кадра и контролируемой задержки показа. **[решено]**
- Масштабирование: несколько стоек сейчас, десятки в перспективе. **[решено]**
- Подключаемые стадии пайплайна: DINOv3 (и любые будущие модели) добавляются позже без переписывания ядра. RT-DETR пока не берём. **[решено]**
- Работа и в облаке, и внутри сети больницы. **[решено]**

Не-цели первой версии:
- Пользователи, организации, пациенты — отдельное приложение, не тема этой платформы. **[решено]**
- Голосовое управление. **[решено]**
- Постобработка — заглушка. **[решено]**
- Сегментация — заглушка. **[решено]**
- DICOM — не ядро; позже экспортный адаптер. **[решено]**, см. §6.
- Соответствие FDA и подобным регуляторным процедурам сейчас не требуется. **[решено]** Законы о защищённых данных (HIPAA, GDPR и аналоги) всё равно действуют. **[моё]**

Анти-цели (провал, даже если технически работает):
- Рамки, «плывущие» относительно изображения на вторичном экране.
- Потеря привязки результата к кадру при перегрузке (допустим пропуск кадров, недопустима подмена).
- Персональные данные в сохранённом видео.

## 3. Условия эксплуатации

- Вход: карта захвата на компьютере у стойки, браузер, WebRTC (getUserMedia). Сигнал 1080p30, реально часто ниже; 4K у единичных стоек. **[решено]**
- Сервер с GPU, в облаке или в сети больницы. **[решено]**
- Задержка вторичного экрана 0,5–1 с и больше допустима, но минимизируется. **[решено]**
- Идентификатор сессии: номер стойки + дата-время старта (плюс случайный UUID для уникальности **[моё]**). Врач выбирается из списка без пароля, его настройки подтягиваются профилем. Пациента определяет внешняя EMR по врачу, стойке и времени. **[решено]**
- Авторизации нет **[решено]**. Защита доступа включается настройкой: в облаке токен стойки плюс TLS, внутри сети может быть выключена. **[моё]**
- TURN входит в поставку. **[моё]**
- Лицензия: код открыт, Ultralytics (AGPL-3.0) используется напрямую; лицензия клиента должна быть AGPL-совместимой. Конкретную лицензию выбирает заказчик. **[решено]** По NOTICE endoscopy-platform лицензия DINOv3 кастомная (Meta), условия проверить до подключения. **[моё]**

## 4. Модели и пайплайн

Состав первой версии **[решено]**:
- YOLO-классификация по кадру: качество, анатомическая зона, режим (например WLI/NBI). Раньше это загонялось в детекцию.
- YOLO-детекция находок (bbox). Сегментация — заглушка.

Позже **[решено]**:
- DINOv3 — оценка тонких структур в области bbox и масок (второй каскад, запускается только при находках). RT-DETR пока не берём. **[решено]**
- PIQE — для редактирования (выбор кадров), не часть потока.

Анатомические связи нужны, но согласуются с YOLO-классификацией зон: зону даёт классификатор, а не детектор. Правила `anatomical_verifier` из прототипа переосмысляются. **[решено]**

Предобработка (опция): кадрирование. Прямоугольник задаётся вручную в начале сессии, потому что изображение, как правило, квадратное, а на остальной площади — техническая информация. **[решено]** По умолчанию выключена. **[моё]**
- Координаты bbox в логе хранятся в системе исходного кадра, прямоугольник кадрирования записывается в заголовок лога. **[моё]**
- Сохраняемое видео — уже обрезанное (заодно убирает наложенный текст с данными пациента); исходный кадр целиком не сохраняется. **[моё]**

Архитектура **[моё]**:
- Каждая модель реализует общий интерфейс «стадия»: вход — кадр или область, выход — типизированный результат с идентификатором кадра. Пайплайн собирается из стадий по конфигу. Рантайм (Ultralytics, потом при необходимости ONNX/TensorRT) скрыт за интерфейсом.
- Приём WebRTC и сессии отделены от пула GPU-воркеров с ограниченной очередью. При перегрузке кадры пропускаются, результат всегда привязан к своему кадру. Состояние сессии не хранится в памяти процесса.
- Стек: FastAPI, aiortc, Celery/Redis, React — как у endoscopy-platform. **[решено]**
- Режим видеофайла проходит через тот же пайплайн и тот же механизм привязки кадров, обязателен. **[решено]**

## 5. Синхронизация кадра и bbox

Корень проблемы прототипа: у кадра на клиенте и на сервере нет общего идентификатора, переживающего видеокодек. Требования **[решено]**: на вторичном экране каждый кадр показывается с небольшой задержкой вместе с результатом для этого кадра.

Предлагаемое решение **[моё]**:
- Буфер выравнивания на клиенте: показ кадра N только когда пришёл его результат или истёк предел ожидания (тогда кадр показывается без рамок, не с чужими).
- Идентификатор кадра, устойчивый к кодеку. Кандидаты: (a) метка с номером кадра в нескольких пикселях верхней строки кадра, читаемая на сервере и затем вырезаемая; (b) передача кадров через WebCodecs/DataChannel с явными номерами. Выбор делается коротким экспериментом в начале проекта.
- Для режима видеофайла идентификатор — просто номер кадра и PTS файла.

## 6. Результат сессии

Канонический формат — самодостаточный контейнер **[решено]**:
- Видео H.264 MP4 без запечённых рамок. **Пишется локально рядом со стойкой (в браузере/на компьютере у стойки) из исходного сигнала карты захвата, а не на сервере**: серверное видео после WebRTC изменено протоколом (перекодирование, потеря кадров, смена битрейта). **[решено]**
  - Идентификатор кадра присваивается на клиенте до отправки в WebRTC; локальная запись ведёт таблицу «идентификатор кадра ↔ PTS в файле» (рядом с видео), чтобы лог сервера привязывался к кадрам записи. Метка в пикселях (если выберем её для сервера) ставится только в копию для отправки и в запись не попадает. **[моё]**
  - Кадрирование применяется к локальной записи тем же прямоугольником. **[моё]**
  - Контейнер собирается у стойки: после завершения сессии клиент забирает лог с сервера и упаковывает вместе с видео. Доставка во внешнюю EMR идёт оттуда. **[решено]**
- JSON-лог (пишет сервер): идентификатор кадра, PTS, bbox, класс, confidence, результаты классификации (зона, качество, режим), прямоугольник кадрирования, версии моделей и таксономии, идентификатор сессии (стойка, время, UUID), врач. Версионированная схема. Деперсонализирован. **[решено]**
- Плеер (специализированный) накладывает рамки поверх видео и позволяет извлекать данные. **[решено]** Включён в план, но после ядра. **[моё]**
- Лог пригоден для возврата в endoscopy-platform как данные для дообучения (кадр + bbox + метки). Формат согласовать с её экспортом YOLO/COCO. **[моё]**

DICOM: на этом этапе не используется. Позже — экспортный адаптер контейнера: Video Endoscopic Image Storage с H.264 (совместимость с вьюерами желательна **[решено]**), лог — отдельным объектом в тех же исследованиях со ссылкой на видео. Конкретный вид лога в DICOM (SR, закодированный JSON) решается тогда. **[моё]**

Если кадрирование выключено, видео сохраняется как есть, ответственность на враче. **[решено]**

Статус моделей: классификаторы (зона, качество, режим) ещё не обучены, обучение займёт порядка пары дней. **[решено]** До этого клиент разрабатывается на детекторах из прототипа и на заглушках классификатора. **[моё]**

Деперсонализация: помимо кадрирования, нужна проверка, что в видео и логе нет персональных данных; стойка может накладывать текст прямо в видео.

## 8. Объём первой версии

Входит: WebRTC и режим файла; кадрирование (опция); YOLO-классификация и детекция; анатомические связи; буфер выравнивания и вторичный экран; запись контейнера (видео + лог); масштабируемый пул воркеров; поставка в контейнерах; TURN.
Не входит: пользователи/пациенты, голос, постобработка, сегментация, DICOM, RT-DETR, DINOv3, плеер (после ядра).

## 8а. Решения автора по итогам проверки строителем (все **[моё]**)

- Задержка и нагрузка: целевая сквозная задержка вторичного экрана около 1 с, размер буфера выравнивания настраивается. Число потоков на GPU определяется замером в начале проекта и закрепляется нагрузочным тестом приёмки; 4K-потоки сжимаются до рабочего разрешения инференса, координаты пересчитываются в исходный кадр.
- Эксперимент по идентификатору кадра: годится, если на тестовых прогонах с изменением битрейта метка читается без ошибок. Иначе берётся запасной вариант (WebCodecs/DataChannel). Эксперимент выполняется первым.
- Устойчивость: локальное видео пишется фрагментированным MP4 (или чанками), лог на сервере построчно (JSONL), так что при обрыве остаются читаемые записи, а при потере связи с сервером видео продолжает писаться. Продолжение сессии после сбоя не нужно. Долгоживущие потоковые сессии не ставятся в Celery; Celery только для фоновых задач (экспорт, пост-обработка).
- Хранение: локальный диск или S3-совместимое хранилище по настройке; срок хранения настраиваемый; отдачу файлов выполняет простой API.
- Режим видеофайла: идёт в реальном темпе через тот же путь, что и поток, и показывается на вторичном экране; дополнительно пакетный режим без привязки к реальному времени для тестов и повторной обработки. Файл загружается через браузер или задаётся путём на сервере.
- Анатомические связи: в первой версии каркас, использующий правила из `anatomy_relations` прототипа поверх зоны от классификатора. Результат пишется в лог как поле и показывается предупреждением. Новые клинические правила не придумываются без врача.
- UI/UX в целом копируется с референса (`video_stream_project/frontend`), кроме отвергнутого в этом документе: голосовое управление, пользователи/организации/пациенты, постобработка, схема синхронизации bbox (Canvas с допуском по времени). **[решено]**
- Клиентская часть: выбор врача и стойки, ручной прямоугольник кадрирования на странице стойки, сигнализация находок цветом и звуком с порогами в профиле врача, Chrome/Edge современных версий.
- Платформа: Linux, NVIDIA GPU, Docker. Образы и веса можно разворачивать без доступа в интернет.
